## v0.9 source isolation and service scheduling — 2026-10-18

Classification: **INCREMENTAL / EMPIRICAL**. Three causes were reproduced: the collector waited for every adapter before publishing healthy sources, fixed interval ticks were skipped during long process reads, and the launchd service ran with default CPU/I/O throttling. Restoring normal Nice priority alone did not remove the throttling. The installed `launchd.plist(5)` documentation identifies Interactive as the classification for services on which app responsiveness depends; this HTTP service has no XPC transaction mechanism for Adaptive classification. The service now uses Interactive and removes the explicit Nice setting. Other jobs are untouched.

Process rounds now dispatch available adapters independently and schedule the next round from the previous round's start. A source publishes when it finishes; a slow source cannot delay another source's next read. Completions within one event-loop turn are coalesced, and unchanged graphs emit health only. Manual `collectOnce()` still awaits the reads associated with its shared round. Readiness resolves on the first usable publication, with unread sources marked as collecting.

Each result carries its captured process observation time separately from its completion time. Freshness and retained-data expiry use observation age; new publication cannot make old evidence fresh. A process-failure epoch invalidates reads that started before failure, even if process discovery recovers before those reads finish. Timeout-ignoring readers cannot overlap or publish late results. Stop cancels active work and suppresses callbacks. Cached nodes are copied before linking and stale decoration. Browser clock ticks detect aged observations without relayout, marking only affected source nodes/edges unless the shared process observation or connection itself is stale.

Health exposes `processTimings` (`tableMs`, `argsMs`, `filesMs`), `processStage` for attributed command failures, `processObservedAt`, and per-source `observedAt`/`updating`. Diagnostics contain timings and stage names, not command arguments or file paths. A collector-level timeout may have no stage attribution if it wins the cancellation race. `collectMs` now reports the maximum recorded process-plus-source read duration across sources; it is not the delay before every source publishes. Thresholds remain 12 seconds for freshness at the default four-second interval, eight seconds per adapter, ten seconds per process observation and two minutes for retained data.

The initial 60-second live baseline included a 4,535 ms collection and a maximum publication age of 6,736 ms. Separate process profiling caught a 9,106 ms observation, with 8,816 ms in the all-process table, 230 ms in argument lookup and 50 ms in open-file lookup. Narrowing descriptor reads did not improve timings; using shortened executable names missed three of 41 agents, so both changes were rejected. Three interleaved priority samples showed a small Nice 5 penalty (262.1 ms median versus 226.9 ms normal), but normal Nice alone still left 15 of 80 live health samples degraded under load averages 125–142. The remaining launchd classification was therefore corrected and measured separately.

Controlled source-isolation comparison: identical synthetic five-millisecond and 250-millisecond adapters, a 100-millisecond interval and 1.6-second observation windows. Across two interleaved runs, first fast-source publication improved from **251–255 ms to 8–10 ms**, fast-source updates increased from **5 to 16**, and maximum update gaps fell from **354–356 ms to 106–108 ms**. These numbers establish isolation, not a guaranteed production speedup.

Live verification after the final service classification: **90 of 90 one-second health samples were current and non-degraded**, with no source errors or collections exceeding four seconds. Reported collection duration was **211–442 ms, median 291 ms**, and the oldest sampled source observation was **3,997 ms** old. Host load averages remained **126–149**. The immediately preceding normal-Nice/default-classification run had a sampled median of **6,412 ms**, maximum **12,833 ms**, and 15 of 80 degraded samples at load averages 125–142. These consecutive observation windows are empirical evidence rather than a randomized benchmark. `launchctl` confirmed the service's spawn type changed from daemon to interactive; the native app showed Current.

Verification: **172 tests passed**, none skipped, with `node --test --test-concurrency=1 test/*.test.mjs`. The original isolation and cadence reproductions failed before the fix and pass afterward. [Collector regressions](../test/collector.test.mjs) cover independent progress, observation age, process timeout/recovery, epoch invalidation, expiry, cancellation and coalescing; [process tests](../test/procs.test.mjs) cover diagnostics without changing ownership/failure semantics; [UI regressions](../test/navigation.test.mjs) cover local aging without relayout. Independent review found no actionable issues, including the service classification. Synthetic browser checks showed a continuously updating source beside a retained failed source, without console errors. The installed native app is 0.9.0, its signature verifies, and its Graph view reconnects to the updated service.

Limits: finite sampling cannot guarantee deadlines under arbitrary host load, sleep or unavailable filesystems. Failed process discovery must still suspend ownership-dependent interpretation rather than invent completed sessions. No process-table cache, longer deadline or hidden stale state was used to make health appear green. Next check: sustained everyday operation, using stage diagnostics if a new outlier occurs.

## v0.6 attention, freshness and performance — 2026-10-18

Classification: **INCREMENTAL / EMPIRICAL**. v0.6 adds a metadata-only turn reducer for Claude (including children), Codex and Pi/OMP. Explicit unresolved input tools and supported approval events request attention; ordinary completed replies do not. Errors/aborts remain failures even when the host process is alive. Direct human-facing final prose questions are conservatively inferred and labeled; subagent prose addresses the parent and does not populate the human queue. Blocking input results or new user messages clear pending requests. Asynchronous acknowledgements do not clear questions; these survive automatic continuation turns until human input or failure. Missing event timestamps fall back to stable file modification times.

Failures remain in Live and have a counter and attention group. Recent completions expire after ten minutes. Search and agent filters apply to attention, with keyboard-operable buttons and a narrow-window toggle. Last-known source data is marked, and no longer animated as current activity.

Each successful collection sends a small health event even when the graph is unchanged. `/api/health` distinguishes `ready` (the dashboard can open), `ok` (current, non-degraded data), `stale` and `degraded`. With the default interval, data becomes stale after 12 seconds. Adapter errors retain last-good nodes for at most two minutes; successful empty results clear them. Adapter deadlines default to 8 seconds and process discovery to 10 seconds. The initial 3/4-second limits were too strict on this host at load average ~130 and were increased after live validation. A timed-out call cannot overlap a new invocation or publish a late result. Process and filesystem access failures never become empty, apparently successful observations.

Fleet collection now limits independent metadata reads to 16 concurrent operations and keeps process/heartbeat checks uncached. An interleaved synthetic fixture (12 runs, 288 workers, 2,304 session files; eight warm samples each) measured median **1,178 ms before → 352 ms after**, approximately **70% lower**. Host load varied substantially: this is fleet-adapter evidence, not a guaranteed whole-dashboard latency improvement. Process-only samples before the change ranged from 540 to 1,470 ms; earlier full live observations ranged from 9–15 seconds under load and later fell below one second before optimization.

Claude and Codex now read independent sessions in batches of eight, preserving graph order and checking process ownership on each refresh. Claude reuses transcript file metadata within the same refresh and reads each session's children sequentially to avoid nested fan-out. A separate synthetic fixture (128 sessions per adapter, plus 128 Claude children; three interleaved warm samples each) measured median **301 → 56 ms for Claude** and **25.5 → 4.4 ms for Codex**. Before/after graphs matched exactly. These are adapter measurements, not an end-to-end speed guarantee; process discovery can still dominate under high system load.

## Evidence and limits

All claims below are `EMPIRICAL` checks against this machine on 2026-10-16.

- **Matching:** All 24 live Claude registry sessions matched their desktop metadata (`cliSessionId`).
  - The desktop `startedBy` links matched `spawnedFrom` across the sampled parent and child sessions.
  - Both running pi processes mapped to the session in their own cwd.
- **Waiting vs. idle (superseded by v0.6 above):** the original registry/recency mapping conflated completed turns with requests. Current adapters use explicit turn/input evidence and labeled final-prose inference.
- **OMP:** in-process L1/L2 children are `working` only while their file changed in the last 60 s; otherwise they are `idle` under a live root.
- **Cross-tool links:** these come only from process ancestry. A Codex thread started by Claude through the desktop app (no shared process tree) is not linked.
- **OpenCode:** not covered. Local storage held only empty `session_diff` files. A process node still appears when `opencode` runs.
- **Historical cost (superseded by v0.9 above):** warm-cache ticks took about 1 s, mostly `ps` and `lsof`, with approximately 1–2 % CPU and 95 MB RSS. Under high system load (load average ~150), ticks slowed and were skipped. v0.9 changes that scheduling behavior; these figures are not current guarantees.
- **Security:** an independent review checked the loopback-only bind, the Host-header guard (403 otherwise), CSP and `nosniff`, escaping of file-derived text, and allow-listing of statuses and edge kinds. A hostile `.fleet/state.json` in a cloned repo was the confirmed attack path; it is fixed and covered by a test.

Classification: **INCREMENTAL**, a local tooling prototype with no research claim.

### Implemented activity, conversation and results

Select a session to read its latest observed event, Chat, and Results. Results includes returned tool output, explicitly final replies where the runtime records that flag, and the latest agent reply (without claiming finality). Tool input/output expands in place. Private thinking/reasoning and system records are excluded. Text is escaped rather than executed; images, HTML and arbitrary files are not opened by the content endpoint.

The server reads only the selected node's known transcript, with a 1 MiB tail and at most 120 normalized entries per read. Claude desktop/registry nodes carry a separate transcript path. Approved source roots are resolved before use; paths outside them and body-os contexts (including cwd aliases) cannot supply content. Common credential formats are redacted as a secondary defense; this is not a general secret-detection guarantee. No transcript content is written into the repository or a new database.

The selected inspector polls every 4 seconds while visible. It keeps up to 400 observed local events across updates and marks that limit when reached. agentsview supplies history in pages of 40; a request is bounded to 4 MiB and each upstream fetch times out after 3.5 seconds. Metadata ID/cwd must match before messages are accepted. A changed archive revision replaces loaded archive pages, because ordinals can be reused during compaction/rebuild; pagination uses the revision that produced its cursor. During ongoing archive updates an earlier page may require a refresh. Disconnected/unindexed/unsupported sources are labeled, and local events remain available independently of the archive. OpenCode/process-only nodes currently have no content reader.

Evidence (`EMPIRICAL`, 2026-10-16): installed agentsview v0.45.0 session metadata, descending message pagination, transcript revision and embedded tool-output fields checked against an Agent Fleet-related session without copying its transcript. 42 automated tests cover formats, branch selection, redaction, stable identities, archive/live merging, pagination, selection races, archive replacement, unavailable sources, file boundaries/aliases, HTTP guards and the existing graph behavior. Synthetic browser checks verified Chat, earlier-message loading and expanded Results. Independent review identified analysis-channel exposure, local-tail rollover loss, pagination gaps/empty-cursor handling, cwd aliases and archive revision mixing; these are corrected and regression-covered. No formal guarantee or cross-runtime completeness claim. Next check: owner use across live Claude/OMP/Pi sessions; native/binary previews remain outside phase 1.

The project graph remains the overview. Its inspector presents observed activity, conversation/tool history and the explicitly attached browser. A previous log entry is not proof of what a process is doing now.
